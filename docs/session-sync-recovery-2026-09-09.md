# 会话同步修复与部署验收

## 根因与修复

新 Flow 网页登录态和兼容 REST 接口的 Labs OAuth 是两个不同的会话。原实现将页面就绪或存在 ST 作为登录成功证据，可能推送仍包含过期/撤销 AT 的 ST；目标接收后仍不能执行任务。

本次变更：

- 浏览器和协议刷新都检查 Labs 有效期（保留 60 秒余量）、邮箱一致性，以及无积分消耗的 credits 鉴权。浏览器校验复用源上下文的代理与 Cookie，协议请求使用源代理，不读取系统默认代理。
- 仅对明确授权失效尝试一次源浏览器 OAuth 续期，遇到二次验证停止并提示人工处理。HTTP 403/429/503 等不明确授权失效的情况不作为强制续期依据。
- Cookie 按 domain/name/path 保存与轮换，排除过期、空值、错误作用域和分区 Cookie。Google 主域 SID/PSID 与 Flow OSID 必须同时有效。支持连续编号的 NextAuth 分段 ST，校验后读取轮换值。
- 不再因目标连接失败、409 独立登录保护或限流清空源 Cookie；目标检查不可用时停止该组同步，避免全账号重登录。源浏览器补全失败时保留上次 Cookie 快照，但本次同步失败，不继续发送旧快照。
- 完整 Flow 同步必须获得目标 Cookie、代理、OAuth 鉴权和账号启用确认。Gemini `gcu` 模式不增加 Flow 专属字段要求。
- 错误日志与同步事件使用分类提示，不保存原始目标错误响应或可能携带凭据的异常字符串。

## 部署后检查

1. 保留挂载的 `data/`、`profiles/`；先升级支持新确认字段的 Flow2API，再部署同步器。无需清库或重新创建 Profile。
2. 每个账号配置目标可访问的 `captcha_proxy_url`。源和目标端口/IP 字符串可以不同，但实际外网出口必须一致；不能自动将源机器 localhost 当作目标机器 localhost。首次同步、OAuth 续期改变 ST 时不能依赖目标按旧 ST 查找代理。
3. 同步一个账号。成功响应应包含 `success=true`、`oauth_verified=true`、`account_active=true`；目标也应显示对应账号、完整 Cookie 和代理配置。
4. 若仍提示过期，在源 Profile 完成 Labs OAuth 和 Flow 登录，必要时人工完成 Google 二次验证。不得通过延长本地过期时间、启用无效账号或反复重放旧 Cookie 代替重新授权。
5. 目标保存成功但仍禁用：检查目标账号的手动禁用状态与自动启用设置。本项目不越权修改目标设置。
6. 409：该账号属于目标独立登录，应在目标 Native Profile 续期；保持两端分离，不通过同步覆盖。
7. 单账号成功后再扩大同步范围，并在目标执行最低消耗的真实生成验收。同步鉴权成功不保证 Google 跨设备会话、任务风控和额度永远可用。

## 本地验证

在仓库根目录运行 `python -X utf8 -m pytest -q`。测试使用模拟响应与 Cookie jar，不访问真实账号，不消耗积分。覆盖浏览器和协议路径、OAuth 过期/身份/AT 校验、完整 Cookie、代理隔离、409/429/503 分类、目标禁用和 Gemini 兼容。

本轮只修改本地代码，未提交、push、部署或执行线上生成。
